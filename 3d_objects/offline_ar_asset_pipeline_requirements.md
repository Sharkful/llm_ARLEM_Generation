# Offline AR Asset Pipeline Requirements

## 1. Purpose

This document defines the initial requirements for an offline asset generation, resolution, packaging, and validation pipeline for AR/XR scenes. The pipeline is intended to support Unity-based AR experiences, including deployment to devices such as the Meta Quest 3.

The system is not intended to generate or retrieve assets dynamically while the AR application is running. Instead, asset resolution, asset creation, conversion, validation, and packaging occur during the development/build process. The runtime AR application loads a resolved scene description and a known set of packaged assets.

The primary goal is to allow an author, script, or LLM-assisted system to describe a scene semantically, then produce a deployable AR scene package containing all assets, materials, textures, runtime JSON, and metadata needed by the Unity application.

## 2. Core Design Principle

The development pipeline should be intelligent, flexible, and iterative. The runtime AR application should be simple, deterministic, and reliable.

In practical terms:

- The authoring layer may contain semantic descriptions, asset specifications, unresolved asset needs, and design intent.
- The build pipeline resolves those needs into concrete assets, prefabs, materials, and runtime instructions.
- The runtime layer should only instantiate known assets using known asset IDs and validated parameters.

The runtime application should not be responsible for interpreting vague asset descriptions, searching for missing assets, generating geometry, resolving licensing, or repairing broken scene specifications.

## 3. Scope

### 3.1 In Scope

The system should support:

- Authoring scene specifications with semantic asset descriptions.
- Resolving requested assets against a local or curated asset catalog.
- Creating asset variants from existing primitives or prefabs.
- Generating simple procedural or parametric assets when appropriate.
- Converting external model files into Unity-ready formats.
- Creating and assigning materials and textures.
- Normalizing scale, pivot, orientation, and bounds metadata.
- Producing resolved runtime JSON for scene loading.
- Packaging assets for use in Unity/Quest builds.
- Generating validation reports.
- Generating scene preview images for human and future automated review.
- Supporting human author review before deployment.

### 3.2 Out of Scope for Initial Version

The initial version does not need to support:

- Runtime asset generation on the AR device.
- Runtime download of missing assets.
- Fully autonomous visual approval.
- Fully autonomous scientific correctness checking.
- AI-generated complex 3D models as a required capability.
- Arbitrary external asset retrieval from unrestricted sites.
- Complex animation authoring.
- Full Unity editor UI tooling.

These capabilities may be considered later if the initial architecture supports them cleanly.

## 4. Conceptual Pipeline

The high-level workflow is:

```text
Authoring scene specification
        ↓
Schema validation
        ↓
Asset requirement extraction
        ↓
Asset resolution
        ↓
Asset generation / retrieval / conversion
        ↓
Scale, pivot, material, and provenance normalization
        ↓
Unity import and prefab/material preparation
        ↓
Resolved runtime JSON generation
        ↓
Package validation
        ↓
Preview rendering
        ↓
Optional image-model review
        ↓
Human author review
        ↓
Deployable AR scene or lab bundle
```

A shorter summary is:

```text
semantic scene → resolved assets → validated bundle → preview → author approval → deploy
```

## 5. Major System Components

### 5.1 Authoring Scene Specification

The authoring scene specification is the flexible, semantic description of the scene. It may be generated by a human, a script, an LLM, or some combination of these.

It may include:

- Object descriptions.
- Desired visual appearance.
- Asset specifications.
- Educational or conceptual intent.
- Approximate sizes.
- Desired interactions.
- Behavior components.
- Placement information.
- Review notes.

The authoring JSON may contain unresolved asset specifications such as:

```json
{
  "object_id": "moon",
  "asset_spec": {
    "description": "a small gray moon with visible crater texture",
    "kind": "sphere",
    "semantic_type": "moon",
    "desired_size_m": 0.15,
    "visual_style": "educational astronomy model"
  },
  "position": [0.8, 1.2, 0.0]
}
```

This file is not intended to be loaded directly by the runtime AR application.

### 5.2 Asset Resolver

The asset resolver is responsible for converting unresolved asset specifications into concrete asset choices.

For each requested asset, the resolver should determine whether to:

- Reuse an existing catalog asset.
- Create a material or scale variant of an existing asset.
- Assemble a composite asset from existing primitives.
- Generate a procedural asset.
- Generate a parametric asset using tools such as OpenSCAD or Blender.
- Import and convert an approved external asset.
- Flag the request for human review.

The resolver should produce a resolution record such as:

```json
{
  "object_id": "moon",
  "requested_asset_spec": {
    "kind": "sphere",
    "semantic_type": "moon",
    "description": "a small gray moon with visible crater texture"
  },
  "resolved_asset": {
    "asset_id": "moon_sphere_basic",
    "resolution_method": "catalog_match",
    "confidence": 0.94,
    "warnings": []
  }
}
```

### 5.3 Asset Catalog

The asset catalog is the authoritative registry of available assets. It should include both built-in core assets and generated/imported assets.

A catalog entry should include, at minimum:

- `asset_id`
- Display name
- Asset class
- Runtime address or package reference
- Material slots
- Canonical bounds in meters
- Pivot location
- Default orientation
- Tags
- Capabilities
- Collider information
- Provenance and license status
- Review level

Example:

```json
{
  "asset_id": "sphere_basic",
  "display_name": "Basic Sphere",
  "asset_class": "primitive",
  "address": "Primitives/Sphere",
  "material_slots": ["surface"],
  "canonical_bounds_m": [1.0, 1.0, 1.0],
  "pivot": "center",
  "default_forward_axis": "+Z",
  "default_up_axis": "+Y",
  "tags": ["sphere", "primitive", "planet", "atom", "marker"],
  "capabilities": {
    "scalable": true,
    "supports_material_override": true,
    "has_collider": true
  },
  "license_status": "approved",
  "review_level": 0
}
```

### 5.4 Asset Builder

The asset builder performs deterministic asset preparation tasks.

It may call tools such as:

- Unity editor scripts.
- Blender command-line scripts.
- OpenSCAD.
- Model conversion utilities.
- Texture processing utilities.
- Validation scripts.

The builder should be responsible for:

- Converting source geometry to Unity-ready formats.
- Creating materials.
- Assigning textures.
- Creating prefabs or prefab variants.
- Normalizing scale.
- Setting pivot/origin conventions.
- Creating colliders when required.
- Recording metadata.
- Updating the asset catalog.

### 5.5 Runtime Scene Loader

The runtime AR scene loader should consume only resolved scene JSON and packaged assets.

It should:

- Load the resolved scene file.
- Load or query the runtime asset catalog.
- Instantiate objects by `asset_id`.
- Apply transform, scale, and material overrides.
- Attach or configure known behavior components.
- Report clear errors if an asset or behavior is missing.

It should not:

- Interpret natural-language asset descriptions.
- Search external repositories.
- Generate geometry.
- Convert STL/FBX/GLB files.
- Resolve licensing.
- Guess missing materials.
- Silently substitute unrelated assets.

## 6. Authoring JSON vs. Resolved Runtime JSON

The system should distinguish between authoring JSON and resolved runtime JSON.

### 6.1 Authoring JSON

Authoring JSON is flexible and semantic. It may contain descriptions and requested asset specifications.

Example:

```json
{
  "object_id": "moon",
  "asset_spec": {
    "description": "a small gray moon with visible crater texture",
    "kind": "sphere",
    "semantic_type": "moon",
    "desired_size_m": 0.15
  },
  "position": [0.8, 1.2, 0.0]
}
```

### 6.2 Resolved Runtime JSON

Resolved runtime JSON is strict and executable. It contains only concrete asset IDs and validated runtime parameters.

Example:

```json
{
  "object_id": "moon",
  "asset_id": "moon_sphere_basic",
  "position": [0.8, 1.2, 0.0],
  "rotation": [0, 0, 0],
  "scale": [0.15, 0.15, 0.15],
  "material_overrides": {
    "surface": "moon_gray"
  }
}
```

The AR application should load only the resolved runtime JSON.

## 7. Asset Classes

The resolver should classify requested assets into asset classes.

### 7.1 Primitive Assets

Primitive assets are simple reusable shapes or elements.

Examples:

- Sphere
- Cube
- Plane
- Cylinder
- Cone
- Torus
- Arrow
- Line
- Label
- Grid

Primitive assets should usually come from the core catalog and should rarely require new geometry.

### 7.2 Material or Scale Variants

Many requested assets can be represented as variants of existing assets.

Examples:

- Red sphere
- Transparent blue shell
- Glowing arrow
- Gray moon-like sphere
- Oxygen atom marker

Variants should generally reuse existing geometry and apply material, scale, or metadata changes.

### 7.3 Composite Assets

Composite assets are assemblies of multiple primitives or existing assets.

Examples:

- Water molecule
- Coordinate axes
- Solar system diagram
- Light ray plus prism diagram
- Inclined plane apparatus

Composite assets may be stored as prefabs or generated from structured scene fragments.

### 7.4 Parametric Generated Assets

Parametric assets are generated from structured parameters using deterministic tools.

Examples:

- Brackets
- Apparatus stands
- Dials
- Cutaway boxes
- Simple lab equipment
- Geometry demonstrations

Possible generation tools include OpenSCAD and Blender scripts.

### 7.5 Imported Assets

Imported assets come from approved local or external sources.

Examples:

- Complex lab equipment models
- Furniture
- Environmental objects
- Realistic props
- Purchased or curated 3D models

Imported assets must include provenance and approved license metadata.

## 8. Asset Scale, Pivot, and Orientation Requirements

Every asset must have a known canonical scale.

The catalog should record:

- Canonical bounds in meters.
- Pivot location.
- Default orientation.
- Forward axis.
- Up axis.
- Unit convention.

The scene author should be able to specify desired size in physical units where appropriate.

Example:

```json
{
  "object_id": "earth",
  "asset_id": "sphere_basic",
  "target_size_m": 0.35,
  "position": [0.0, 1.2, 0.0]
}
```

The build pipeline or resolver should convert target size into runtime scale values based on canonical asset bounds.

This requirement is intended to prevent unknown-scale assets from entering runtime scenes.

## 9. Materials and Textures

Materials and textures are a major part of the asset pipeline and require further specification.

Initial requirements:

- Assets should define named material slots.
- Scene objects may override material slots.
- Materials should have stable IDs.
- Texture references should be validated at build time.
- Missing textures should produce warnings or errors, not silent runtime failures.
- Transparent, emissive, metallic, and rough/smooth materials should be represented explicitly.
- Material definitions should be compatible with the Unity render pipeline being used.

Example material reference:

```json
{
  "material_overrides": {
    "surface": "transparent_blue_shell"
  }
}
```

Example material definition:

```json
{
  "material_id": "transparent_blue_shell",
  "shader_family": "URP/Lit",
  "base_color": "#6aa8ff",
  "alpha": 0.25,
  "metallic": 0.0,
  "smoothness": 0.8,
  "transparent": true,
  "emissive": false
}
```

Additional work is needed to define the full material and texture schema.

## 10. Behavior Components

Behavior components should be handled separately from asset definitions.

Assets should not need to list every possible behavior they are allowed to use. Instead, behavior compatibility should be defined by a behavior schema.

Example behavior schema entry:

```json
{
  "behavior_type": "Rotator",
  "required_components": ["Transform"],
  "parameters": {
    "axis": "vector3",
    "speed_deg_per_sec": "float"
  }
}
```

Example scene object behavior:

```json
{
  "object_id": "moon",
  "asset_id": "moon_sphere_basic",
  "components": [
    {
      "type": "Rotator",
      "parameters": {
        "axis": [0, 1, 0],
        "speed_deg_per_sec": 5
      }
    }
  ]
}
```

The validator should determine whether the target object satisfies the requirements of each behavior.

For example:

- `Rotator` requires only a transform.
- `ClickToShowLabel` may require a collider.
- `GrabInteractable` may require a collider and interaction component support.
- `FlowAlongPath` may require path data.

## 11. Licensing and Provenance

External assets should only be retrieved from approved sites or curated local repositories.

Every imported or generated asset should include provenance metadata.

Required provenance fields may include:

- Source type
- Source URL or local source path
- Original author, if applicable
- License
- License status
- Attribution requirement
- Modification history
- Date imported or generated

Example:

```json
{
  "asset_id": "lab_table_01",
  "source_type": "external_approved",
  "source_site": "approved_asset_repository",
  "source_url": "...",
  "license": "CC0",
  "license_status": "approved",
  "attribution_required": false,
  "modified": true,
  "modifications": [
    "converted to GLB",
    "reduced polygon count",
    "normalized scale"
  ]
}
```

No asset with unknown or unapproved licensing should enter a deployable scene or lab bundle.

## 12. Validation Requirements

The pipeline should produce validation reports before deployment.

Validation should include at least the following categories.

### 12.1 Schema Validation

- Authoring JSON matches authoring schema.
- Resolved runtime JSON matches runtime schema.
- Asset catalog entries are valid.
- Behavior component parameters are valid.

### 12.2 Asset Completeness

- Every `asset_id` referenced in resolved JSON exists.
- Every material ID exists.
- Every texture reference exists.
- Every behavior type exists.
- All required package files are present.

### 12.3 Scale and Geometry

- Every asset has known canonical bounds.
- Object scale is within acceptable limits.
- Pivot is defined.
- Orientation is defined.
- Triangle count is below defined thresholds.
- Mesh import succeeded.
- Collider configuration is valid.

### 12.4 Licensing and Provenance

- All external assets have approved license status.
- Attribution requirements are recorded.
- Unknown-source assets are rejected or flagged.

### 12.5 Runtime Readiness

- Resolved scene contains no unresolved asset specifications.
- Runtime JSON contains only supported fields.
- Package contains all required assets.
- The runtime loader can instantiate all objects.

## 13. Preview Generation

The build pipeline should generate preview images as standard output.

Preview images are intended to support:

- Human author review.
- Debugging of scale and layout problems.
- Future image-LLM review.
- Documentation and scene thumbnails.

Possible preview types:

- Default learner viewpoint.
- Author overview viewpoint.
- Top-down view.
- Side view.
- Object bounds/debug view.
- Thumbnail contact sheet of major assets.

Debug previews may include:

- Object names.
- Bounding boxes.
- Pivot markers.
- Scale reference markers.
- Camera/viewpoint markers.

Preview generation should not be considered a replacement for in-headset testing, but it should catch many obvious layout, scale, visibility, and missing-asset issues.

## 14. Optional Image-Model Review

Automated visual review using an image-capable model is not required for the initial pipeline, but the architecture should support it later.

The image review system could inspect preview images and produce comments such as:

```json
{
  "visual_review_status": "warning",
  "issues": [
    {
      "object_id": "label_moon_phase",
      "issue": "Label may be too small to read from the default view.",
      "suggested_fix": "Increase text scale or move label closer to the learner viewpoint."
    }
  ]
}
```

Future versions may allow the LLM to propose or apply scene patches based on visual review results.

## 15. Review Levels

Not all assets require the same level of review.

Suggested review levels:

- Level 0: Known core asset; no review required beyond standard validation.
- Level 1: Material, scale, or color variant; quick preview review.
- Level 2: Generated simple geometry; author visual review required.
- Level 3: Imported complex asset; author visual review and provenance review required.
- Level 4: Scientifically or pedagogically critical asset; expert review required.

The review level should be recorded in the asset catalog and build report.

## 16. Scene Bundles and Lab Bundles

The system should support both individual scene bundles and larger lab bundles.

### 16.1 Scene Bundle

A scene bundle contains one resolved scene and any scene-specific assets.

Possible contents:

```text
scene.resolved.json
asset_catalog.scene.json
assets/
materials/
textures/
build_report.json
preview_images/
```

### 16.2 Lab Bundle

A lab bundle contains multiple related scenes and shared assets.

Possible contents:

```text
lab.json
asset_catalog.lab.json
shared_assets/
scenes/
  scene_01/
  scene_02/
  scene_03/
```

Example lab manifest:

```json
{
  "lab_id": "moon_lab",
  "title": "Phases of the Moon",
  "scenes": [
    {
      "scene_id": "moon_orbit_intro",
      "file": "Scenes/01_moon_orbit/scene.resolved.json"
    },
    {
      "scene_id": "moon_phases",
      "file": "Scenes/02_phases/scene.resolved.json"
    }
  ],
  "shared_catalog": "asset_catalog.lab.json"
}
```

The runtime should be able to resolve assets from:

1. Core application catalog.
2. Lab-level catalog.
3. Scene-level catalog.

## 17. Error Handling

The system should avoid silent fallback behavior.

Build-time errors should be clear and actionable.

Examples:

- Missing asset ID.
- Missing material ID.
- Missing texture file.
- Unsupported behavior component.
- Invalid scale.
- Unknown license.
- Failed model conversion.
- Missing canonical bounds.

Fallback behavior may be allowed during development but should be explicitly recorded in the build report.

Example:

```json
{
  "status": "warning",
  "message": "Requested texture 'moon_craters.png' was not found. Used fallback material 'moon_gray'.",
  "requires_author_review": true
}
```

Deployable bundles should not contain unresolved errors.

## 18. Role of the LLM

The LLM may assist with:

- Creating authoring scene JSON.
- Interpreting semantic asset requests.
- Searching or ranking catalog matches.
- Writing asset specifications.
- Suggesting material definitions.
- Generating parametric asset scripts.
- Interpreting validation failures.
- Suggesting fixes.
- Reviewing preview images in later versions.

The LLM should not be the sole authority for:

- Licensing approval.
- Scientific correctness.
- Final visual approval.
- Runtime asset availability.
- Package completeness.

LLM outputs should be validated by deterministic schemas, build checks, and human author review where appropriate.

## 19. Initial Implementation Priorities

A practical first version should focus on the following:

1. Define authoring JSON and resolved runtime JSON distinction.
2. Build a minimal asset catalog schema.
3. Support core primitive assets with known scale and material slots.
4. Support material overrides.
5. Support behavior component references through a behavior schema.
6. Resolve asset specifications into asset IDs.
7. Validate missing assets, materials, textures, behaviors, and scale.
8. Generate resolved runtime JSON.
9. Generate preview images.
10. Produce build reports.

A first useful version does not need full external asset search or advanced generated geometry. It should prove the basic architecture using primitives, variants, composites, and a small curated asset library.

## 20. Open Questions and Areas for Further Design

The following areas require additional design work:

### 20.1 Asset Attribute Schema

The system needs a more complete definition of asset attributes, including:

- Physical role.
- Interaction role.
- Educational role.
- Visibility requirements.
- Material slots.
- Anchor points.
- Label locations.
- Animation readiness.
- Collider expectations.

### 20.2 Material and Texture Schema

The material and texture system needs more detail, including:

- Shader families.
- Render pipeline compatibility.
- Texture channels.
- Normal maps.
- Transparency handling.
- Emission.
- Tiling and UV assumptions.
- Procedural textures.
- Fallback policies.

### 20.3 Asset Creation Methods

The pipeline needs a clearer specification of how new assets are created, including:

- Procedural Unity primitives.
- OpenSCAD generation.
- Blender Python generation.
- STL/OBJ/FBX/GLB conversion.
- Composite prefab assembly.
- External asset import.
- Asset normalization.

### 20.4 Preview Rendering Method

The system needs a decision about how previews will be generated:

- Unity editor camera renders.
- Standalone renderer.
- Simplified Python/three.js viewer.
- In-app screenshot mode.

### 20.5 Runtime Packaging Method

The system needs a decision about the package mechanism:

- Built-in Resources.
- Addressables.
- AssetBundles.
- StreamingAssets.
- Custom local catalog.

### 20.6 Human Review Workflow

The system needs a defined author review process:

- Where previews are shown.
- How comments are captured.
- How revisions are requested.
- How approval status is recorded.
- How approved bundles are locked for deployment.

## 21. Summary

The proposed system is an offline AR asset pipeline that converts semantic scene specifications into validated, deployable AR scene or lab bundles.

The central architectural choice is to separate:

- Semantic authoring JSON.
- Asset resolution and build-time processing.
- Strict resolved runtime JSON.
- Packaged Unity-ready assets.

This allows the LLM and development tools to provide flexible, intelligent assistance while keeping the runtime AR application deterministic and reliable.

The initial implementation should emphasize canonical scale, strict validation, curated assets, material overrides, preview generation, and clear human author review. Advanced generation, external asset retrieval, and image-model visual review can be added later without changing the core architecture.
